# 自进化的两条路：改 harness，还是改验收

这份文件说的是这套系统自进化的路数，以及它和别人那套（直接改 harness、改喂给模型的那段上下文）
差在哪儿。
不谈实现，只说这两种做法各自换来什么、代价是什么。

## 1. 别人的做法：改 harness 与上下文

主流那一套是白盒的：结果不如预期，就去改它那一侧——harness（跑模型的那套东西：工具、循环、怎么装载
skill）或者上下文（喂进模型的那一段：skill.md、提示、记忆、示例）。下一次它更可能做对。

它换来的是**agent 自己变强**：改的东西长在 harness 里，跟到哪儿带到哪儿，换一件活也还在。

它的性质是：

* **效果是统计的**。改完只能说"以后大概会好些"，说不清这条改动管住了哪一类做错；
* **不能拿过去的事故去检验**。上一次做砸的时候还没有这条提示，你没法把那次原样重放一遍，看它响不响；
* **一条提示对所有活一起生效**，所以它说不清自己管什么、不管什么；
* **改的是 harness，不是验收**。系统本身还是老样子：这个 agent 变强了系统就好，换个模型就得重来。

## 2. 这套系统的做法：改验收

结果不如预期时，先不动 harness，先问两件事：

* **合规**：哪一条法律没拦住它？这条法律该怎么写才拦得住？
* **制度**：这一次活的组织方式对不对？这一步该不该有、谁做、在谁之前、做完给谁看？

改的是验收那一侧：法律（规则）和制度（工单、成员表）。harness 本身一个字不动。

一句话对照：**别人让 agent 更可能做对，我们让做错的东西过不去。**

要紧的性质是：模型可以一直很弱。只要不合预期的交付过不去，这场会就还能用。改进落在环境上，
所以换一个更弱的模型也能跑——代价是这套环境会越长越厚。

## 3. 这类自进化当场可证伪

这是它和改提示最不一样的地方：

* 一条修完的法律，**拿过去那些做砸的例子跑一遍**，规则响不响立刻就知道；
* 白盒提示改完，只能等以后再跑几次，靠感觉说它有没有用。

所以要紧的不是"规则能跑"，而是**事故本身变成了用例**：每条规则旁边放一份当初没过的交付，
规则一改就拿它跑一遍。事故一件件攒起来，规则集自己就是一份回归用例集；这是"更容易再审查"的来处。

改提示没有这个性质：提示的效果只能往前看，不能往回试。

## 4. 两处修法，管的东西不一样

**合规**管的是交出来的那份东西：这份不合格、说清哪里不合格、再做一版。它作用在交付物上。

**制度**管的是这次活怎么组织：这一步该不该有、该谁做、该在谁之前、做完要不要给人看。
它作用在单子和成员表上，改完以后同类活的组织方式都变了。

同一场事故，两处都能修：东西不行改一版，组织不行改流程。多数自进化只有前一处，
所以它只能一遍遍要求重做，而改不动"我们为什么让它这么干"。

## 5. 代价，要说在前面

* **官僚**。法律越攒越多，模型一点没变好，环境越来越严，活被拖慢。攒到某个程度，人会开始绕过它。
* **agent 会学着绕**。数参数的规则，靠嵌套函数和一层包装就能字面合格、东西更差。所以每条规则
  得写明它管什么、不管什么，还要有人负责把它管宽——不是加条数，是把口子堵上。
* **代价不对等**。一条坏提示只是没用；一条坏法律会挡住活，而且被拦住的那一方没法跟它讲理。
  所以法律要能退休：谁把它撤下来、什么时候撤，得是明文，不能靠没人再提它。
* **法律不是越多越安全**。一条管得宽的（跑测试、类型通）顶十条管表面的；管表面的越攒越像白盒提示，
  只是换了个地方写。

## 6. 这些代价我们算进去了：法律与制度由谁审

上面那些代价不是没想到，而是专门留了一个位置盯着它们：一个**高阶的审核 agent**。它和会里的 critic
不是一回事：

* critic 判的是**一次交付**——这份不合格，说清哪里不合格，再做一版。它的结论是一个 bool 加一句话。
* 审核 agent 判的是**法律和制度本身**——一段时间里的事故、异议、重做、被绕过的记录是它的依据。
  它的结论是"改哪一条、撤哪一条、往设施要哪一样基础 api"。

它盯四件事：

1. **规则有没有可绕的口子**。字面合格、东西更差的那种绕法，它要找到并堵上；每条规则管什么、
   不管什么，由它写成明文。
2. **规则和用例对不对得上**。当初没过的那份交付，现在还拦得住吗；拦不住的，说明规则被改坏了，
   或者本来就没写对。
3. **规则有没有过期**。挡了不该挡的活，得有人把它撤下来；撤下来也要签字，不能靠没人再提它。
4. **事故是不是制度的问题**。同一类事故反复出现，那多半不是干的那个人的错，而是这一步不该这么走、
   该换个成员做、该拆成两步。

它对干活的模型什么都不说：它不教 harness（教 harness 是改 harness 与上下文那一侧的事），
它改的是法律与制度；需要新的基础 api 的时候，它往设施那一侧提需求，不自己在制度里造一个。

**它是人那一侧的放大镜，不是自己拍板的**：基础 api 的增删、法律的立与撤，最后仍然由人签字。
它存在的意义是把那些代价摆到台面上：官僚还是官僚，但不会悄没声地积起来。

它的依据都在盘上（规则、用例、单子、记录、每一次重做），所以它拿数据说话，不靠印象；这也是这套
自进化和改提示那一侧最大的不同：**能被审查**。

### 审规范这件事，跑的还是同一场会

制度和法律不在跑程序的那个仓库里：它们在**自己的规范仓库**里（那几类文件：api、工单、规则、请求、
成员表）。这个仓库叫什么、放在哪儿，由用它的人定——设施按配置去找它，不假定它的名字。
独立带来三样：干活的仓库和立法的仓库分开，各走各的历史；谁改了哪一条查得到；签字的人也不一样。

要改那个仓库，不必另起一套设施：同一套工单、进度、值、成员表、critic 照样跑，换的只有两样——
盯的东西从"一份交付"换成"这个仓库"（法律、用例、事故记录），干活的成员换成一个**高阶审核员**
（也许是人，也许是一个强基模）。审规范这件事本身也能写成几张单：读这一段法律和它拦过、漏过的东西，
提出改法，把改法送审，落盘。

### 审核是递归的

产生法律和制度的那道审核，本身也可以被审：换的只是盯的东西和干活的成员，设施不用变。
这就是 RSI——一层改一层。往上套几层、在哪儿停，由人定：每一层的产出都落在盘上、可查、要签字，
人签字那一步就是收敛点。

## 7. 通用性丢在哪儿

这套做法确实比 skill.md 少一点通用性，但要说清是谁丢的：**不是"可执行"丢的，是"写在交付物的
表面特征上"丢的**。

* 写在已经定下来的那些基础 api 上，这条法律还通用，换一件事照样成立；
* 每遇到一次事故就加一个专用算子、写一条只认这一次的规则，规则集就跟提示一样脆。

所以基础 api 的正交与张成不是风格偏好，是这套办法能不能收敛的前提：不正交，法律会互相重叠、
说不清谁负责；不张成，每件新事故都得先往设施里加一个基础 api，制度得排队等设施。

这也是这套分工里最慢的一环：**制度的进化受基础 api 增补速度的限制**。别的做法里，这条改动当场
就写进 skill.md 了；这里得先问"这个基础 api 有没有、合不合规矩"，慢，但慢出来的东西能被审查。

## 8. 落在编程上为什么容易收敛

因为交付物能**自己跑**：测试过不过、类型通不通、跑起来对不对。这是不靠人写规则就有的验收。

由此有一条取舍：**让验器偏"跑"，别偏"读"**。

* 读文本的规则（数几行、有没有某个写法）会过拟合到那几次事故上，写起来快、管得窄；
* 跑出来的结论（这一版跑不过它自己的测试）不会过拟合，写起来难、管得宽。

边界也说清楚：交付物不可判的时候（写一段说明、做一个设计），验器没有抓手，这套办法只剩下制度
那一半——组织方式还能改，"这份到底好不好"判不了。那种活上，白盒那一路反而更有用。

## 9. 使用纪律

这套办法不是装上就能用，用的人得守这几条；缺一条，它就会按第 5 节说的那样慢慢烂掉。

* **用例与规则放在一起**。现在规范仓库里只有规则，没有当初没过的那些交付；没有用例，规则改完
  只能靠再试一次去感觉，跟白盒提示就没差别了。
* **每条规则写明管什么、不管什么**，以及谁负责把它管宽。
* **法律能退休**：撤下来也要有人签字，不能靠没人再提。
* **基础 api 的增补走设施那一侧，慢一点**：别为一次事故加一个，先问它是不是别人也会用到。
