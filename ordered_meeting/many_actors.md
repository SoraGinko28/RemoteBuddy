# 一个角色坐两个人：工单里那一步归谁

现在一场会一个 actor 服务、一个 critic 服务。会议可以声明不止一个成员在同一个角色上
（`agent_name2role`，`normalize_agent_role_map` 只要求至少一个 actor），那时工单里同一步归谁做，得先有
说法。这份文档把三种说法摆出来，说清各自要什么、和现在这套代码差在哪。

## 现在是什么样

- 工单里一步要的只是一个**算子名**（`write_code`），不看谁：谁的能力表里有这个名字，谁就能接
  （`service.answer_service` 只看 `caps`；`plan.due` 只看要读的答没答）。
- 一个 actor 服务 = 一张能力表 + 会议里那个 agent（`live_service` + `MeetingChannel`）。一场会现在
  只有一个终端、一个 agent（`agent_ordinal=1`，`store.meeting.actor_name()`）。
- 所以"多个 actor"今天跑不起来，不是代码挡着，是**会里只有一个 agent 在干活**，第二个人没有自己的
  工作区和终端。

## 说法一：能力表一样，谁先答谁算

两个人各是一个服务，能力表相同（都实现 `actor_api`）。一份工单摆在那儿，谁先跑到谁算，另一个下次跑到
那一步直接回放（`replayed` 不是干活）。这就是 viba 原本的读法：一步归"能力表里有那个名字的那一侧"。

要什么：每个 actor 服务配一个自己的 agent（自己的工作区、自己的终端会话），并且会上要能同时有不止一个
`agent_ordinal`。哪一步谁做的，看 store 里那条数据路径的结果，看不出是"哪个人"做的——要能分得清，就得
在会议记录里记下是哪个服务答的（现在记的是服务名，两个服务同名就混了，所以服务名要按成员取）。

适合：两个人干的是同一种活，谁有空谁上。

## 说法二：api 分家，工单里点名

每个成员一张自己的 api（`actor_a_api`、`actor_b_api`），工单里写 `actor_b.write_code` 就是要 B 做。
一步归谁从**程序文本**就看得出，不用猜。

要什么：`workflow/actor_api.viba` 拆成几份；工单按成员写；`ROLE_OF_API` 那张"哪个 api 归哪个角色"的表
要改成"哪个 api 归哪个成员"（`ticket_centered/workflow.py:46`）。会议记录里"谁答的"也就自然分得开。

适合：两个人的活本来就不一样（一个写第一版、一个改），或者流程要指定谁做。

## 说法三：发单那一侧点名

api 还是一张，工单里多一个 `$who`（成员名）作为实参，谁的名字在里面谁接。

要什么：`answer_service` 挑单时多看一眼 `$who`；发单那一侧（`plan` / `assistant`）要知道点谁。一步归谁
写在工单的 `$call` 里，查起来和说法二一样清楚。

适合：流程固定，但"谁做"这件事要在开会时按情况定。

## 先要定的是什么

不是代码怎么写，是**一步归谁**这件事的语义归哪儿：

- 归**能力表**（说法一）：程序里看不出谁做，看谁快；
- 归**程序文本**（说法二）：写工单的时候就把人点死；
- 归**发单那一侧**（说法三）：发单时按情况点。

三种都要先解决同一件事：会里得能有第二个 agent（第二个工作区、第二个终端会话），现在一场会只有一个。
这一步不做，三种说法都落不了地；这一步做了，说法一几乎不用改代码。
