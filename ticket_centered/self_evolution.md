# 你来做自进化：先看这些

你是这份流程的自进化负责人。你要改的是 `workflow/` 那一层（三份角色 api、工单、规则）；判你的有
四样：**结构、硬断言、账、人**。这份文件说的是它们长什么样、以及你会踩什么坑。

## 1. 你在系统里的位置

* **你的材料**是这套系统本身：`workflow/` 那五类文件、会议记录、store、每个成员包里那份原件、journal。
* **你的产出**是一份候选设计（一个目录）：三份 api + 工单 + 规则。它的名字是
  `Workflow.load(dir).digest()`。
* **你不改正在跑的会**：一张工单发出去，包里带着 `program/`，就钉在发单那一刻的版本上。你改的是
  "下一张发什么"——这正是"新版本够不到正在跑的会"这句话的实现方式。
* 你不是自己判自己：判你的是第 2、3、4 节那四样。

## 2. 结构：你造不出新效果

`interpret` 自己不带实现，一段 viba 能调到的算子**一个都跑不出这张能力表**：

* 一张工单只能调这 7 个算子——actor 的 `acknowledge` / `write_code` / `report_done` / `revise_code`，
  assistant 的 `stated_task` / `closing_note`，critic 的 `judge`；
* 一条规则只能调 critic 表里那三个叶子——`code_under_judgment` / `widest_parameters` / `within_limit`；
* 你往 api 文件里**加**一个新算子声明也没用：声明在 viba 里，实现在表里（Python），加声明只会让那一步
  **永远递延**——工单板上那一格永远不 ✓，发单的那一侧等到超时。

所以想量一个新东西（"函数有没有超过 15 行"）不是你能在 `workflow/` 里办到的：那要动能力表。
你手上能做的是**重组既有算子**：怎么排、接在谁后面、判什么、哪张工单在什么条件下该发。

## 3. 账：你做的事都留下可查的痕迹

| 现象 | 在哪 |
|---|---|
| 这一场会跑的是哪份流程、哪一版这一侧的代码 | 会议记录第 2 行：`- 这份流程：<流程摘要>（这一侧的代码：<能力面摘要>）`（`Workflow.digest()` + `host.capability_digest()`） |
| 每张工单发给了谁、发出去的那份程序是什么 | `tickets/<工单>/<成员>/program/`（包里带着那一刻的程序，源码就是凭据） |
| 谁答了哪条数据路径下的哪个算子 | 会议记录里每个成员自己写的账：`- <成员>（<角色>）答了 <数据路径> + <算子>`（`member.run_bundle`） |
| 各成员包里那份副本与会议 store 一不一致 | `Meeting.reconcile()` |
| 谁答了不属于自己名下的算子 | `Meeting.audit()`：按"算子归哪个角色"核对上面那些账 |

你要审自己改出来的东西，看的就是这两个摘要（流程、能力面）跟上一场是不是同一个，和 `audit()` 有没有
话说。

## 4. 人：能力表与 ADT 是人签字的

* **能力表的增删**（新算子、新叶子、新实现）＝ 人签字；系统只负责把"谁动了什么"摆到人面前。
* **ADT**（`MEETING_ADT.md`）＝ 类型的规格，不归你改。
* 你交出候选设计，人（或一个独立的评审流程）决定并还是不并。

## 5. 有一条你必须先知道

如果你对这个仓库有写权限，你就能改代码、改能力表、改账——**写在文档里的任何"你不许"都挡不住你**。
真正的边界只能由运行环境给：只给你 `workflow/` 的写权、仓库其余部分对你只读，或者你在另一个检出里
改、由人把候选并进来；跑会议的进程从一份受信的检出启动。

于是：**能不能拦住是权限的事，能不能看出来是这边的事**——摘要变了、账对不上、副本不一致，这三样会
留在会议记录里。

还缺的（别当成已经有了）：没有一条"提案"的数据路径或工单（你是在仓库里改，不是通过会议交提案）；
没有自动的评审 + 并入流程；能力面那张"算子 + 谁实现"的清单还不是一个可以直接签字的文件（现在是三份
api 文件加两个摘要）。

①是硬门：它按第 7 节的规矩断言，并且用真的解释器、真的 store、真的规则、真的成员进程把五张工单走完。
③跑完会留在页面上（默认 `--finish leave`），会话头部「工单 n/5」按钮点开是同一份东西。

## 7. 设计的规矩（测试里是硬断言）

* 五类文件：三份角色 api + `tickets/*.viba` + `rules/*.viba`；一张工单至少 import 它要调的那些 api；
* 一张工单里每一步只写**调用**（不重复定义类型）；有 `__ret__`；
* 调到的算子必须在它 import 的那份 api 里；
* **数据路径都相对案子**：设计文件里不许出现带 `/` 的路径，也不许出现案子名；
* 规则是程序：`environ` 进、bool 出，有自己的 `__ret__`。

## 8. 你会踩的坑（都付过代价）

1. **viba 只跑 `__ret__` 拉得着的东西。** 几步要接成链（`$after …` / `$code …`），否则那一步
   **永远不发生**——`write_a_draft` 里"回一句知道了"就这么丢过一次。
2. **两步不能落在同一条 (数据路径, 算子) 上**：第二条会**回放**第一条的答案，不重跑。区分靠
   `$env (environ.sub_env << "…")` 换个名字（现在每步一个：`greeted`、`drafted`、`judged`…）。
3. **并集在实参/字段位置要加括号**：`<- $x (mc.A | nil)`；不加就漏到顶层（`MEETING_ADT.md` 里犯过；
   viba 的结合性是 `**` > `*` > `|`）。
4. **"该发哪一张"** = 要读的都有答案 ∧ 自己的答案一个都还没有 → 你的设计必须是 DAG；一张工单不能把自己
   已经答过的路径再答一遍（那样它永远不该发）。
5. **同刻多张都该发时，次序是文件名字典序**（`workflow.tickets()`，不是流程序）。现在这五张同一时刻只有
   一张该发，所以顺序无所谓；你新写的时候要么保持这个性质，要么把编号编进文件名。
6. **判语**：`objection` 是 critic 的 `judge` 写下的（合格时是空串）。工单指向不存在的 (路径, 算子)，
   成员进程会以"那一步还没答"失败——现场在 journal 的 `ticket_ran` 输出、以及工单板上那一格没有 ✓。
7. **actor 的 `write_code` / `revise_code` 真会叫 agent**（花钱、耗时）；判语合格时 `revise_code`
   直接照原样返回、不再叫。
8. **要交哪个文件**：页面那条路是从**人类第一句话点名的文件名**取的（`quicksort.py`）；你换产物，
   得跟人类那句话对得上，否则发单被拒（409 "没点名要交哪个文件"）。
9. **`is_complete` 还没接**：现在挡住明显写错的是第 6 节那一层测试。

## 9. 现场在哪

```
runs/<会议号>/ticket_centered/meeting_record.md     流程摘要 + 能力面摘要、每张工单、每个人自己的账
runs/<会议号>/ticket_centered/store/                材料：每条数据路径下一条 Prepare（$call / $measured）
runs/<会议号>/ticket_centered/tickets/<工单>/<成员>/ 每个成员那份原件（program/ + store/）——对账靠它们
runs/<会议号>/streams/events.jsonl                  journal：state/ticket_issued、state/ticket_ran
GET /api/meetings/<会议号>/tickets                  页面那块板子（该发哪一张、谁答的、判语、记录）
```
